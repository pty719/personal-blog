## 2. 友链监控 Agent（主动型 Agent）

### 设计
```
BackgroundScheduler（后台线程，不阻塞）
  ├── cron 触发器：每天 8:00
  └── 启动时立即跑一次（部署即见效果）

check_all_friends():
  遍历 friends 表 → httpx.head(url, timeout=5) 探测
  → 状态码 <400 = is_active=True；异常/超时 = False
  → 更新 last_check → 前端显示"⚠️ 可能失效"
```

### 三个关键点
1. **BlockingScheduler vs BackgroundScheduler**：前者阻塞主线程（uvicorn 起不来！），后台任务必须用 Background
2. **普通函数用 SessionLocal()**：定时任务没有请求上下文，不能 Depends(get_db)——和工具函数一个原则
3. **单点失败不影响整体**：try/except 包住单个探测，一个挂了其他照常

### 面试话术
> "我给博客做了友链监控：APScheduler 定时巡检，HEAD 请求探测友链存活，失败自动标记并记录检查时间。这是主动型 Agent——不需要用户触发，到点自己干活。"

## 3. 限流防护（成本控制）

### 防护顺序 = 花钱顺序
```
Pydantic 校验（422，超长直接挡）→ IP 限流（429）→ 会话轮数（429）→ 才调 DeepSeek
```

### IP 限流（内存版）
```python
_calls = defaultdict(list)   # {ip: [时间戳]}

def check_rate_limit(ip, limit=10, window=60):
    now = datetime.now()
    _calls[ip] = [t for t in _calls[ip] if now - t < timedelta(seconds=window)]
    if len(_calls[ip]) >= limit:
        return False
    _calls[ip].append(now)
    return True
```
- **429** = HTTP 标准"Too Many Requests"
- 局限：重启清零、单进程准确——**生产用 Redis**（演进思路 = 加分点）

### 会话轮数
```python
msg_count = db.query(Assistant).filter(Assistant.conversation_id == conv_id).count()
if msg_count >= 100:
    raise HTTPException(429, "会话已达上限，请新开对话")
```
（利用已有 assistants 表 + conversation_id，零新表）

### 面试话术
> "AI 助手是公开接口，我做了三层防护防刷：Pydantic 限制输入长度、IP 限流（10 次/分钟，超限 429）、会话轮数上限。所有检查都在调 LLM 之前，不花钱就先挡掉。内存版限流有局限，生产要换 Redis——这是演进路线。"

## 4. 本阶段最值钱的排查（chat_completion 返回类型 bug）

### 症状
AI 助手突然全部返回"AI 服务暂时不可用"（本地 + 服务器都这样）

### 排查过程（完整复盘）
```
① 先测 DeepSeek key → 200 正常（key 没问题）
② 直接驱动 event_stream 生成器 → 正常输出错误事件（try/except 生效）
③ uvicorn 里请求 → 第一条事件后流断（IncompleteRead 82 字节）
④ 发现 8000 被幽灵进程占着（PID 61824，测试一直打在旧代码上）
⑤ 换 8001 干净环境 → 确认代码行为：错误事件 + done（兜底生效）
⑥ 深挖：为什么总是"不可用"？→ chat_completion 返回 content 字符串
   但 run_agent 需要 message 对象（msg.get("tool_calls")）
   LLM 想调工具时 message 只有 tool_calls 没有 content → KeyError → 兜底误触发
```

### 根因
**公共函数返回语义不统一**：`chat_completion` 被两个调用方使用——
- run_agent（ReAct）：要整个 message 对象（含 tool_calls）
- 文章摘要：只要 content 字符串

修复：统一返回 message 对象，调用方自己取 `resp["content"]`。

### 三个教训（面试能讲）
1. **兜底会吞错误**："AI 服务暂时不可用"掩盖了 KeyError——排查时先问"是上游挂了还是代码 bug"（直接测 key = 最快定位）
2. **公共函数的返回类型要文档化**：一个函数被多处调用，返回什么必须明确，否则埋雷
3. **测试先确认环境**：端口被幽灵进程占着，测试结果全是假象——先确认"我在测谁的代码"
