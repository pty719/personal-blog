# 网站部署从零到上线：小白教学文档

> 以「小站」部署到阿里云为例（2026-08 实战复盘）
> 适合：第一次部署网站的人。读完你不仅能照做，还能理解每一步"为什么"

---

## 0. 部署是什么（先建立直觉）

**比喻**：你的项目 = 装修好的房子（本地开发），部署 = 把房子搬到"营业场所"对外开门营业。

| 本地开发 | 部署上线 |
|---|---|
| 房子在你家（localhost，只有你能看） | 搬到商业街（公网 IP，全世界能看） |
| 自建水电（SQLite + 开发服务器） | 接入市政（MySQL + nginx 正式服务） |
| 随时改装修（代码随便改） | 装修要报备（改代码要重新部署） |

**核心认知：部署不是"传上去就完"，而是"用生产环境把项目跑起来 + 验证"**——环境变了（数据库、静态文件、端口），必须再验一遍。

---

## 1. 部署前的准备（1 小时）

### 1.1 本地把项目调好 ✅

部署前必须满足：
- [ ] 后端接口全部调通（本地测试脚本全过）
- [ ] 前端 `npm run build` 能成功（产出 dist/）
- [ ] 数据库设计确定（本教程用 MySQL）

**为什么**：如果本地都是半成品，部署后问题会叠加，根本没法排查。

### 1.2 准备服务器

买一台云服务器（阿里云等），拿到：
- **公网 IP**（如 ***REMOVED-ROTATED***）
- **SSH 账号密码**（root + 密码）
- 记得在**安全组**放行要用的端口（80 是网站默认端口）

### 1.3 生成部署包（核心产物）

部署包 = 让服务器"一键跑起来"的所有文件：

```
deploy/
├── docker-compose.yml      # 编排：定义有哪些服务、怎么连接（"施工图纸"）
├── backend/Dockerfile      # 后端镜像配方（"装修图纸"）
├── frontend/Dockerfile     # 前端镜像配方（多阶段：构建 + nginx）
├── frontend/nginx.conf     # 网页服务器配置（静态文件 + /api 转发）
└── .env.example            # 环境变量模板（密码/密钥）
```

**Docker 是什么**：把你的项目连同运行环境打包成"集装箱"（镜像），任何机器上一键运行，不污染服务器原有环境。三个集装箱 = 三个服务：

```
容器1: mysql     （数据库，数据持久化在卷里）
容器2: backend   （FastAPI 后端，Python 环境）
容器3: frontend  （nginx：网页文件 + 转发 /api 给后端）
```

## 3. 详细步骤（照着做）

### 第 1 步：本地验证部署包（强烈建议，能省 1 小时）

```bash
cd deploy
docker compose config          # ① 检查编排文件语法
docker compose build           # ② 本地真实构建镜像（验证 Dockerfile 没错）
```

**为什么本地先构建**：Dockerfile 有 bug（路径、依赖）在本地 5 分钟暴露；传上服务器再炸，来回排查 1 小时起步。**我们这次就靠它抓到一个 bug**（见第 4 节坑 1）。

### 第 2 步：上传到服务器

```bash
# 本地执行（把项目传到服务器 /opt/blog）
scp -r backend frontend deploy root@你的IP:/opt/blog/
```

> 小项目用 scp；项目大了写 paramiko 脚本（自动上传 + 执行 + 验证，本教程配套脚本见 deploy/deploy.py）

### 第 3 步：服务器装 Docker

```bash
# 不要用官网命令 curl get.docker.com！国内服务器会被墙（我们踩过）
# 用阿里云源：
apt-get update -y
apt-get install -y ca-certificates curl gnupg
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://mirrors.aliyun.com/docker-ce/linux/ubuntu/gpg | gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://mirrors.aliyun.com/docker-ce/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" > /etc/apt/sources.list.d/docker.list
apt-get update -y
apt-get install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
systemctl enable --now docker
```

### 第 4 步：配镜像加速（国内服务器必做）

不配的话拉镜像（python/node/mysql 基础镜像）会慢到怀疑人生：

```bash
mkdir -p /etc/docker
cat > /etc/docker/daemon.json <<EOF
{"registry-mirrors": ["https://docker.m.daocloud.io"]}
EOF
systemctl daemon-reload && systemctl restart docker
```

### 第 5 步：填环境变量（.env）

```bash
cd /opt/blog/deploy
cp .env.example .env
# 编辑 .env，填两个值（生成随机密码：openssl rand -hex 32）
nano .env
```

`.env` 里是 MySQL 密码和 JWT 密钥——**服务器上的机密，别提交到 git**。

### 第 6 步：一键启动（核心命令）

```bash
cd /opt/blog/deploy
docker compose up -d --build    # -d 后台运行；--build 先构建再启动
```

首次会拉镜像 + 装依赖，5-20 分钟。看进度：

```bash
docker compose ps               # 三个容器都 Up = 成功
docker compose logs -f backend  # 看后端日志（建表、启动）
```

### 第 7 步：验证（全链路，一步都不能少）

```bash
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1/          # ① 网页
curl -s http://127.0.0.1/api/health                                # ② API
curl -s http://127.0.0.1/api/moments                               # ③ 数据库链路
# ④ 登录
curl -s -X POST http://127.0.0.1/api/auth/login -H "Content-Type: application/json" -d '{"username":"admin","password":"你的密码"}'
# ⑤ SPA 路由刷新不 404（前端路由要 nginx 配 try_files 回退）
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1/admin
```

**最后浏览器打开 http://你的IP 走一遍完整流程**（注册/登录/发内容/刷新页面）。

## 4. 部署中的坑（我们全踩过，你直接看答案）

### 坑 1：Docker 构建报 "COPY xxx not found"

```
ERROR: "/nginx.conf": not found
```

**原因**：Docker 的 `COPY` **不能引用构建上下文之外的文件**。nginx.conf 放在了 `deploy/frontend/`，但构建上下文是 `frontend/`。

**解决**：把 nginx.conf 移到 `frontend/` 目录内。

**教训**：这就是"本地先 build"的价值——这个 bug 在本地 5 秒暴露，没传到服务器。

### 坑 2：装 Docker 失败 "Connection reset by peer"

```
curl: (35) Recv failure: Connection reset by peer
```

**原因**：`get.docker.com` 官网脚本在国内服务器被墙。

**解决**：用阿里云 docker-ce 源（见第 3 步）。

### 坑 3：MySQL 起不来 "timeout waiting for dependencies"

```
Container blog-mysql Error dependency mysql failed to start
```

**原因**：MySQL **首次启动要初始化数据目录（我们实测 6 分钟）**，而 docker-compose 的健康检查只等了 50 秒（retries 10 × 5s）就判定失败，导致依赖它的 backend 没启动。

**解决**：MySQL 其实一直在正常初始化——等它 healthy 后重跑一次：
```bash
docker compose up -d    # 这次 MySQL 已就绪，backend 能通过依赖检查
```

**教训**：数据库首次初始化慢是常态，healthcheck 超时时间要留足（或初始化完成后重试）。

### 坑 4（最大的坑）：服务器内存爆了，SSH 都连不上

**症状**：前端页面能打开（HTTP 200），但 API 超时、SSH/Workbench 全部连不上，ping 却正常。

**原因**：2G 内存的服务器同时跑两个项目（AI 伴侣的 MySQL + 小站的 Docker MySQL）→ **OOM（内存耗尽）→ 系统级卡死**，连 sshd 都没资源响应。

**排查过程**：
```
前端 200 + API 超时 + SSH 连不上 = 服务器还活着但资源耗尽
```

**解决**：
1. 阿里云控制台「重启实例」（强制重启，不需要 SSH）
2. 重启后立刻登录，停掉非必要的服务释放内存：
```bash
systemctl stop 旧项目服务
systemctl disable 旧项目服务    # 禁止开机自启，防止重启后又爆
free -m                        # 确认内存释放
```
3. 小站服务（Docker 容器）会自动恢复（restart: unless-stopped 策略）

**教训**：
- 2G 内存跑两个 MySQL 必爆，**部署前先算内存账**
- 服务器卡死时优先用**控制台重启**（Workbench/SSH 都依赖系统响应）
- `systemctl disable` 防止服务开机自启是长期解法

### 坑 5：8080 和 80 端口的选择

**症状**：新服务想用 80 端口，但 80 已被旧项目占用 → 容器起不来 `port is already allocated`。

**解决**：多项目共存用不同端口（8080）；旧项目退役后再切回 80 独占。

## 5. 上线后的常规操作

### 改默认密码
```bash
# 改数据库里的 admin 密码（正规做法是加"改密接口"）
# 临时方案：登录服务器，进 MySQL 容器执行 UPDATE
docker exec -it blog-mysql mysql -uroot -p你的密码 blog
UPDATE users SET password_hash='<bcrypt哈希>' WHERE username='admin';
```

### 以后改代码怎么重新部署
```bash
cd /opt/blog/deploy
docker compose up -d --build    # 增量构建（依赖层有缓存，很快）
docker compose ps
```

### 数据备份（防丢）
```bash
docker exec blog-mysql mysqldump -uroot -p你的密码 blog > blog_backup_$(date +%Y%m%d).sql
```

## 6. 术语表（小白必懂）

| 术语 | 一句话解释 |
|---|---|
| **Docker 容器** | 把项目和运行环境打包的"集装箱"，任何机器一键运行 |
| **Docker 镜像** | 容器的"模板"（代码 + 环境），build 一次可反复运行 |
| **docker compose** | 编排多个容器的工具（一条命令启动全部服务） |
| **端口** | 服务器的"门牌号"：80 是网页默认，3306 MySQL，8000 后端 |
| **反向代理（nginx）** | 前台接待员：网页请求直接服务，/api 请求转给后端 |
| **SSH** | 远程登录服务器的通道（命令行操作） |
| **安全组** | 云服务器的"门禁"：放行哪些端口能被外网访问 |
| **OOM** | 内存耗尽：程序申请内存失败被杀（服务器卡死的常见原因） |
| **swap** | 用硬盘当"虚拟内存"缓冲，内存不够时的救命稻草 |
| **SPA 路由回退** | 前端框架的路由刷新时会 404，nginx 要配置 try_files 兜底 |

## 7. FAQ

| 问题 | 回答 |
|---|---|
| 部署一定要用 Docker 吗？ | 不是。也可以用 systemd 直接跑（见 AI 伴侣部署配方）。Docker 的优势：环境隔离、一键复现、不污染服务器 |
| 本地和服务器环境不一样怎么办？ | 用 Docker 就是"环境一致"的解法；不用 Docker 就要手动对齐 Python 版本/依赖 |
| 服务器 2G 内存够吗？ | 一个项目够；两个 MySQL 会爆（我们实测）。部署前 `free -m` 看看 |
| 为什么前端要 npm run build？ | Vue 源码浏览器看不懂，要编译成静态文件（dist/）才能被 nginx 服务 |
| 改了代码怎么更新？ | 重新 build（前端）+ `docker compose up -d --build` |
| 数据会丢吗？ | MySQL 数据在 Docker 卷里（容器删了数据还在）；定期 mysqldump 备份最保险 |

---

## 8. 一句话总结

**部署 = 本地调好 → 打包（Docker）→ 上传 → 服务器一键起 → 全链路验证 → 上线后监控。**

坑都在"环境差异"里：国内网络（装 Docker/拉镜像）、内存预算（多项目 OOM）、服务启动时序（数据库初始化慢）——**本地先验证部署包 + 部署后逐项 curl 验证**，能避开 80% 的坑。
