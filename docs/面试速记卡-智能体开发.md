## 卡 1：项目介绍（开场 2 分钟）

**问题**：介绍一下你的项目。
**标准答案结构**：一句话定位 → 技术栈 → 我负责的 → 核心亮点（埋钩子）→ 公网地址
**要点**：
> "FastAPI + Vue3 + Docker 部署公网的全栈应用。核心亮点是内置 **ReAct 架构的 AI 助手**——大模型自主调用站内工具：**RAG 语义检索**文章知识库（从 TF-IDF 升级到 **embedding**）、查库、**SSE 流式**输出、带会话记忆。另有两个自动化 Agent：定时爬 AI 新闻、巡检友链。http://***REMOVED-ROTATED*** 公网可访问。"
**纠错点**：❌ 不说技术栈 → ✅ 主动吐技术词（ReAct/RAG/SSE/embedding）当"钩子"引导面试官追问你准备好的方向。

## 卡 2：ReAct 循环原理

**问题**：大模型怎么"决定"调工具？循环流程？
**标准答案**：
> "最多 5 轮：① 完整对话历史发给模型（LLM 无状态）② 模型看 **TOOLS 说明书**决策——直接回答或返回 tool_calls ③ 要调工具：模型消息（含 tool_calls）追加历史 → call_tool 执行 → 结果作为 **role=tool 消息（带 tool_call_id）**追加 ④ 带新历史再问模型——看到工具结果后继续调或给最终回答。5 轮上限防死循环。"
**纠错点**：❌ "TOOLS 定义返回类型" → ✅ TOOLS 定义的是**参数（parameters 入参）**——告诉模型怎么调；❌ "结果加在 tool_call 里" → ✅ 结果独立 role=tool 消息追加。

## 卡 3：多工具调用 + 为什么再发一轮

**问题**：一条回复要调两个工具怎么处理？结果返回后为什么还要发一轮？
**标准答案**：
> "双层循环：外层 5 轮 = ReAct 轮次；内层 for 逐个执行 tool_calls，**每个结果 append 一条** role=tool 消息（各自 tool_call_id），全部收集完**一次性**发新请求（continue 回外层）。为什么再发：模型第一轮只声明'要调工具'**没回答用户**；工具结果模型从没见过，必须喂回去让模型'读'完组织回答——这是 Agent 不瞎编的原因。"
**纠错点**：append 在 for 内（对！）vs 发请求在 for 外（continue 实现）——两层结构讲清是加分点。

## 卡 4：会话记忆

**问题**：记忆存哪？请求怎么带？长对话怎么办？
**标准答案**：
> "三层：① 会话层：后端生成 conversation_id（uuid）经 SSE 首条事件给前端存 **localStorage**——游客匿名会话（不是用户标识！）② 存储层：SQLAlchemy 存 MySQL（conversation_id/role/content），请求按 id 查历史拼 messages ③ 长对话：阈值触发**摘要压缩**——早期消息（长期记忆）LLM 压成 summary 存库，近期（短期记忆）完整保留，控制请求体 token。"
**纠错点**：❌ "给用户设唯一标识" → ✅ 是**会话标识**（没登录哪来的用户）；✅ **摘要压缩已实现**（>20 条触发，最早消息 LLM 压成 role=summary 滚动更新，失败降级全量）——面试可讲"已实现"。

## 卡 5：SSE vs WebSocket

**问题**：流式输出用的什么？为什么不用 WebSocket？
**标准答案**：
> "SSE（Server-Sent Events）。对比：SSE 服务器→客户端**单向**推、基于 **HTTP**、浏览器**自动重连**、简单；WebSocket **双向**、独立协议、要自己写心跳重连。AI 回答是'服务器推文字'的单向场景，SSE 天生匹配且 nginx/代理友好——**杀鸡不用牛刀**；多用户实时协作（共同编辑/聊天室）才需要 WebSocket。"
**纠错点**：❌ 不了解 WebSocket → ✅ 必须会对比（记忆锚点：SSE=收音机单向广播，WS=双向电话）；加分：SSE 事件流设计（type: tool/text/done——工具透明性）。

## 卡 6：防刷/限流（花钱边界）

**问题**：公网开放怎么防人刷 API 烧钱？
**标准答案**：
> "原则：**所有防护在调 LLM 之前**（不花钱先挡掉）：① Pydantic 校验 content 1~500 字，超长 422（路由层自动拦）② IP 限流：同一 IP 10 次/分超了 **429**；内存版开发够用，**生产换 Redis 分布式** ③ 会话轮数 100 条（50 轮）防无限追问。三层都挡在 chat_completion 之前——恶意请求一次大模型都调不到。"
**纠错点**：❌ "Pydantic 检索请求" → ✅ **校验**（validate）；❌ 漏 429 状态码 → ✅ Too Many Requests 是专业信号；❌ 漏"花钱边界"叙事 → ✅ 这是此题精髓。

## 卡 7：TF-IDF vs Embedding

**问题**：为什么 RAG 从 TF-IDF 升级到 embedding？
**标准答案**：
> "TF-IDF 是**字面检索**——分词数字符次数，同义词/换说法就断；embedding 把文本映射成**语义向量**，意思相近方向相近，算向量相似度。真实例子：用户问'微积分里研究**变化率**的概念'，文章写'**导数**反映变化速率'——字面无'变化率'，TF-IDF 匹配不上；embedding 理解'变化率≈导数'能命中。选型：fastembed+bge-small-zh（约150MB）vs torch（800MB）——2G 服务器资源权衡；块少用 numpy 余弦，量大换 FAISS（接口不变）。"
**纠错点**：❌ 只背概念不给例子 → ✅ 例子必须带（变化率→导数）；⚠️ 例子选"字面完全无交集"的最有力。

## 卡 8：工具合并（真实 debug）

**问题**：两个搜索工具怎么变一个了？遇到过模型调错工具吗？
**标准答案**：
> "search_articles（关键词）和 search_knowledge（RAG 全文）功能重叠 → 模型**决策摇摆**。排查：先试把 RAG 放 TOOLS 前面（位置偏好）→ 不行 → 最终**去掉关键词工具**。功能重叠 = 扩大模型决策空间；被删能力被保留工具覆盖（RAG 索引含标题+正文）——功能没丢只是收敛。**工具设计原则：职责单一、互不重叠、减少 LLM 决策空间。**"
**纠错点**：这是"真 debug 过"的回答（背不出来）——保持！补理论化收尾（职责单一/决策空间）。

## 卡 9：生产事故（五段叙事）

**问题**：出过生产事故吗？怎么排查解决？
**标准答案**（现象→排查→根因→解决→预防）：
> "**现象**：跑一周后所有接口 500、SSH 连不上。**排查**：① docker compose ps 发现 MySQL **unhealthy** ② 后端日志 Can't connect to MySQL（后端活、库挂了）③ MySQL 日志 InnoDB 长 **semaphore wait**（内部卡死）④ free -m 2G 内存耗尽。**根因**：小机器 MySQL 默认配置随运行时间累积吃内存 → OOM。**解决**：重启实例 + 显式限内存（buffer 64M/连接 50/关 performance schema）。**预防**：小内存机器必须显式限内存（写进 compose）；监控 unhealthy 预警。"
**纠错点**：❌ "我靠的 AI"（面试大忌——讲排查动作不讲工具）；❌ 只讲现象+解决 → ✅ 五段齐全，排查思路是价值。

## 附：通用应试技巧

1. **任何技术点都带真实例子**（项目里全是现成的）
2. **结论理论化收尾**："这告诉我：工具职责要单一 / 防护要在花钱之前 / 小内存机器要算资源账"
3. **埋钩子**：开场主动吐技术词（ReAct/RAG/SSE/embedding），把面试引到你准备好的战场
4. **没实现的别说"已实现"**：说"设计了、演进中"（如摘要压缩）——诚实 + 设计思维同样加分
5. **事故题不说工具说动作**："查容器状态→看日志→看内存"（AI 辅助是过程，叙事聚焦排查思路）
