# 小站部署指南（Docker Compose 一键上线）

> 版本：v1.0 ｜ 服务器：阿里云 99 元机（Ubuntu 24.04）｜ 架构：mysql + backend + frontend 三容器
> 前置条件：本地已全部调试验收（后端 16 接口 ✅、前端 9 页面 ✅、npm run build ✅）

---

## 0. 部署架构（先看懂再动手）

```
公网用户
   │ :8080（80 已被 AI 伴侣占用，小站用 8080 共存）
   ▼
nginx 容器（frontend）──────────┐
   ├── /        → 前端静态文件（dist/ 构建产物）│
   └── /api/    → 反代 → backend 容器 :8000 ──→ MySQL 容器 :3306
                                              （compose 内部网络，不暴露公网）
```

**三个容器**：`blog-mysql`（数据持久化）/ `blog-backend`（FastAPI）/ `blog-frontend`（nginx）。

**关键点**：
- 对外只开 **8080** 端口（80 被 AI 伴侣的系统 nginx 占用，勿动！）；后端 8000、MySQL 3306 只在 Docker 内部网络
- **安全组要放行 8080**（阿里云控制台 → 安全组 → 添加 8080 入方向规则）
- 数据在 `mysql_data` 卷里（容器删了数据不丢）
- 部署包在本地 `D:\blog_project\deploy\`（已生成并本地校验通过）

## 2. 第二步：上传到服务器

需要把**整个项目**（backend/ + frontend/ + deploy/）传到服务器。推荐放 `/opt/blog/`：

```bash
# 服务器上先建目录（假设你是 root）
mkdir -p /opt/blog
```

本地 → 服务器传输方式（任选）：
- **scp**：`scp -r D:\blog_project\* root@服务器IP:/opt/blog/`
- **paramiko 脚本**：自动上传 + 远程执行 + 验证（推荐，一键）

> 我可以用 paramiko 写一个 deploy.py 帮你全自动（上传 → 装 Docker → 起服务 → 验证），你只需要提供 SSH 凭证。

## 3. 第三步：服务器一键起服务

### 3.1 装 Docker（Ubuntu 24.04 一条命令）

```bash
curl -fsSL https://get.docker.com | sh
systemctl enable --now docker
```

### 3.1.5 配置镜像加速（国内服务器必做！）

阿里云等国内服务器**直连 docker.io 拉镜像极慢甚至失败**（本地 Windows 拉 90MB 要 10+ 分钟，服务器同理）。

```bash
# 用阿里云容器镜像服务加速器（免费，需要阿里云账号控制台查看专属地址）
# 控制台：容器镜像服务 → 镜像加速器 → 复制你的专属地址 https://xxxx.mirror.aliyuncs.com
mkdir -p /etc/docker
cat > /etc/docker/daemon.json <<EOF
{
  "registry-mirrors": ["https://你的专属加速地址.mirror.aliyuncs.com"]
}
EOF
systemctl daemon-reload && systemctl restart docker
```

> 没有阿里云账号就用公共加速地址（百度搜索"docker 镜像加速"可找到可用地址）。
> 不配置的话 `docker compose build` 会卡在拉镜像，这是国内部署第一坑。

### 3.2 配置 .env（唯一的"手工活"）

```bash
cd /opt/blog/deploy
cp .env.example .env
# 编辑 .env，填两个值：
#   MYSQL_ROOT_PASSWORD=你的强密码
#   JWT_SECRET=随机 32+ 位字符串（生成：openssl rand -hex 32）
nano .env
```

> JWT_SECRET 生成命令：`openssl rand -hex 32` 输出一串随机 hex，粘进 .env。
> 这两项是安全底线：MySQL 密码别用弱密码，JWT_SECRET 别用默认值。

### 3.3 构建并启动（核心命令）

```bash
cd /opt/blog/deploy
docker compose up -d --build
```

首次构建要下载镜像 + 装依赖，约 5-10 分钟。

### 3.4 查看状态

```bash
docker compose ps            # 三个容器都 Up = 成功
docker compose logs -f backend   # 看后端日志（建表/管理员创建）
```

## 5. 常见坑（部署必踩，提前知道）

| 坑 | 症状 | 解决 |
|---|---|---|
| **SPA 刷新 404** | 点 /admin 能进，F5 刷新就 404 | nginx 配 `try_files $uri $uri/ /index.html`（已配 ✅） |
| 后端连不上 MySQL | backend 日志 `Can't connect` | `depends_on` 的 `condition: service_healthy`（已配 ✅）；MySQL 启动慢时可 `docker compose restart backend` |
| 容器里访问数据库 | `localhost:3306` 连不上 | 容器里必须用**服务名** `mysql:3306`（已配 ✅） |
| 数据丢了 | 容器删了数据没了 | 用 volume `mysql_data`（已配 ✅） |
| 80 端口被占 | frontend 起不来 | 服务器上先 `ss -tlnp \| grep :80` 查占用（宝塔/nginx 残留） |
| 中文乱码 | 数据变 ??? | 连接串加 `?charset=utf8mb4`（已配 ✅） |

## 5.5 生产事故复盘：MySQL 卡死导致全站数据接口 500（2026-09-02）

### 事故现象
- 公网文章/项目/说说页打开**空白无内容**（前端 200，数据接口全 500）
- API 返回 `Internal Server Error`，后端日志：`Can't connect to MySQL server on 'mysql' (Connection refused)`

### 排查过程（4 步定位）
```
① docker compose ps → 发现 blog-mysql 状态 unhealthy（已 7 天）
② 后端日志 → "Can't connect to MySQL"（后端活着，是 MySQL 挂了）
③ docker logs blog-mysql → "A long semaphore wait: waited 1199 seconds"
   （InnoDB 内部卡死——运行 7 天累积的资源问题）
④ free -m → 2G 内存 used 1250M / available 仅 362M（内存耗尽边缘）
```

### 根因
**2G 小内存机器上 MySQL 用默认配置长期运行**：
- InnoDB buffer pool 默认 128M+，随运行时间增长占用
- 数据量/连接累积 → 内存压力 → InnoDB 长信号量等待（卡死）→ 拒绝连接
- restart MySQL → InnoDB 崩溃恢复吃内存 → **系统 OOM 卡死**（SSH 都连不上）

### 处理步骤
1. 阿里云控制台**重启实例**（恢复系统，容器自动拉起，数据在 volume 不丢）
2. **给 MySQL 显式限内存**（根治），docker-compose.yml mysql 服务加：
```yaml
command:                                        # 2G 内存机器必配
  - --innodb-buffer-pool-size=64M               # InnoDB 缓冲池降级（默认 128M+）
  - --max-connections=50                        # 连接数上限（博客够用）
  - --performance-schema=OFF                    # 关性能监控表（省内存）
```
3. `docker compose up -d mysql`（重建容器，数据在 volume 不丢）
4. **重启 backend** 重连新 MySQL（容器重建后连接池失效）
5. 验证：`articles/moments API 200` + `SHOW VARIABLES LIKE 'innodb_buffer_pool_size'` → 67108864（64M ✅）

### 修复后效果
- 可用内存 504M → **742M**（MySQL 吃得更少）
- MySQL 内存上限锁定，不会再随运行时间膨胀

### 预防清单
- [x] MySQL 内存参数显式限制（buffer pool 64M / 连接 50 / 关 performance schema）
- [ ] 监控：每周看一眼 `free -m` + `docker compose ps`（unhealthy 是预警信号）
- [ ] 长期：换 4G 实例或 MySQL 换 SQLite（数据量小可选）

### 面试话术（生产事故排查）
> "我处理过一次生产事故：MySQL 在 2G 单机上跑了一周后 InnoDB 卡死，所有数据接口 500。排查：先看容器状态（unhealthy）→ 后端日志（连不上 MySQL）→ MySQL 日志（长 semaphore wait）→ 内存（耗尽）。处理：重启实例恢复，然后给 MySQL 显式限制内存（buffer pool 64M、关 performance schema），之后稳定运行。**教训：小内存机器部署数据库必须显式限制内存，默认配置会随运行时间累积占用直到 OOM。**"
